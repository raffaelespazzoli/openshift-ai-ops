- (decision) Why force: pain to solve (SRE alert fatigue, slow manual diagnosis, institutional knowledge loss) + opportunity to capture (frontier LLMs + deep OpenShift knowledge enable closed-loop AI ops that generic vendors cannot match).
- (capability) CAP-1: Alert intake and triage — receive AlertManager webhooks, deduplicate, correlate into Root-Cause Events, maintain priority queue. Covers FR-1, FR-2, FR-3.
- (capability) CAP-2: AI-driven root-cause diagnosis — orchestrator agent forms hypotheses, queries cluster via read-only MCP Server, retrieves operational knowledge (runbooks, RHOKP, Learning Store, agentic skills), produces structured diagnosis with root-cause code and confidence. Covers FR-4, FR-5, FR-6.
- (capability) CAP-3: Adversarial validation — skeptic agent challenges every diagnosis and every remediation plan in one round of structured debate; stability under challenge = acceptance. Covers FR-8, FR-9.
- (capability) CAP-4: Policy-gated remediation — immutable diagnosis crosses RBAC airlock, remediation planner produces structured plan (steps, blast radius, rollback, risk), dry-run pre-flight validates, policy gate evaluates severity × blast radius × confidence, human approval when required, serialized execution with cooldown. Covers FR-10 through FR-17.
- (capability) CAP-5: Outcome-driven learning — every incident stored as Case Record with vector embeddings; temporal decay reduces confidence of old/version-mismatched records; fast-path bypasses LLM for high-similarity past successes. Covers FR-18, FR-19, FR-20.
- (capability) CAP-6: Operational web UI — standalone web app showing incident list, pipeline detail view (triage → diagnosis → skeptic → remediation → execution → outcome), approval workflow, and summary dashboard with operational metrics. Covers FR-21, FR-22.
- (capability) CAP-7: Eval harness — simulated alert injection, accuracy measurement against known-correct answer keys, domain-level trust gating for auto-remediation. Covers FR-24, FR-25, FR-26.
- (capability) CAP-8: Self-contained deployment — single Helm chart, no CRDs, no OLM, per-agent LLM configuration, complexity-based model routing, semantic cache, LLM retry with backoff. Covers FR-27, FR-28, FR-29, FR-30, FR-31, FR-32.
- (capability) CAP-9: Versioned REST API — single contract between backend and all UI surfaces, authentication via OpenShift OAuth, audit-logged state changes. Covers FR-33.
- (capability) CAP-10 (POST-MVP): Domain specialist agents — self-selecting agents per domain (compute, storage, network) with label-matching rules. Covers FR-7.
- (capability) CAP-11 (POST-MVP): OpenShift Console plugin — dynamic plugin surfacing incident list, detail, and approval within the native Console. Covers FR-23.
- (constraint) RBAC Airlock: diagnosis agents use read-only cluster access (cluster-reader SA, --read-only MCP Server); remediation uses read-write (cluster-admin SA, separate MCP Server instance). No cross-access.
- (constraint) No CRDs, no OLM — self-contained Helm deployment avoids depending on the cluster's API extension machinery.
- (constraint) Serialized remediation: one remediation executes at a time (global lock), configurable cooldown between consecutive executions.
- (constraint) Default-deny policy: all remediations require human approval out of the box. Auto-execution must be explicitly enabled per severity/blast-radius/confidence combination.
- (constraint) No automatic rollback — rollback is human-triggered only; triggered rollback is stored as a failure signal in the Learning Store.
- (constraint) Single-cluster scope (v1): no cross-cluster aggregation, federated learning, or fleet-wide views.
- (constraint) Must function when the managed cluster is partially degraded — self-contained persistence, no dependency on cluster API machinery for the tool's own operation.
- (constraint) Adversarial validation is mandatory — every diagnosis and remediation plan must survive skeptic challenge before proceeding. Not optional.
- (constraint) Evidence artifacts required for auto-execution — concrete log lines, metric values, resource states supporting the diagnosis. Auto-execution blocked without evidence regardless of policy matrix.

- (decision) RHOKP integration resolved: deploy RHOKP (Solr container, 600k+ docs) + okp-mcp (MCP server) as sidecar deployments in the Helm chart. Agents query knowledge via MCP streamable-http — same transport as the OpenShift MCP Server. Offline-capable, no external API dependency. Eliminates need to chunk/embed docs into pgvector at build time. pgvector still owns case records and fast-path. This adds two deployments to the pod topology (RHOKP Solr + okp-mcp). Refreshed by updating the RHOKP container image. Source: github.com/rhel-lightspeed/okp-mcp.
- (note) Architecture impact: AD-13 (Unified RAG via pgvector) needs revision. Runbooks and RHOKP are no longer chunked/embedded into pgvector. Instead, agents query RHOKP via okp-mcp (MCP search_portal and get_document tools) and runbooks via the same or similar mechanism. pgvector retains case records, semantic cache, and fast-path. AD-9 (pod topology) grows from 5 to 7 deployments: add rhokp (Solr) and okp-mcp.
- (decision) Eval harness scenario library resolved: seed from openshift/runbooks repo — each runbook maps an alert name to diagnosis steps and remediation actions, which can be structured into scenario + expected-answer pairs. Augmented over time with hand-authored scenarios from real incident patterns and production case records promoted to eval scenarios after human validation.
- (decision) LLM endpoint requirements resolved: specify required capabilities, not specific models. Required capabilities: (1) tool use / function calling — agents invoke MCP tools and agentic skills, (2) structured output — diagnosis and remediation plans must conform to JSON schemas, (3) multi-step reasoning — causal chain construction and adversarial challenge. Model selection (which family, which tier per agent role) is a deployment decision, not a spec constraint.
- (decision) Multi-tenancy resolved: cluster-scoped only. The tool serves the ops team responsible for cluster health, not individual tenant teams. Consistent with non-goals (no app-layer diagnosis), target user (SREs with ops responsibilities), and RBAC model (cluster-reader/cluster-admin ServiceAccounts). Namespace-scoped views are not needed in v1.
- (decision) MTTR baseline resolved: the organization's pre-existing MTTR tracking provides the baseline. The tool must track its own MTTR (alert firing to alert resolution for handled incidents) so the organization can compare. No specific target number — success is that MTTR trends lower after adoption. This is already a requirement via CAP-6 (summary dashboard shows MTTR) and the success signal.
