- (decision) AD-1: Design paradigm = staged pipeline. The outer system shape is a directed pipeline (alert → triage → diagnosis → remediation → execution → observation → learning). Each stage has typed input/output contracts. The RBAC Airlock is a hard stage boundary (diagnosis→remediation). Agent orchestration (orchestrator/specialists/skeptic) is internal to the diagnosis and validation stages, not a system-level pattern. LangGraph's directed graph is the runtime expression. Fast-path bypass and re-challenge loops are conditional edges, not a different paradigm. Prevents: stages being built as loosely-coupled event subscribers with unclear ordering; agent internals leaking into the pipeline contract.
- (decision) AD-2: Remediation SA = cluster-admin by default. Two ServiceAccounts: cluster-reader (diagnosis MCP Server, read-only) and cluster-admin (remediation MCP Server, read-write). Rationale: remediation actions are not knowable in advance — the tool must be able to act on any cluster resource the planner proposes. Helm chart exposes SA/ClusterRoleBinding as configurable values so teams can substitute a tighter custom ClusterRole. Dry-run pre-flight (FR-12) catches permission gaps regardless of which role is bound. Prevents: remediation failures due to insufficient permissions blocking incident response; teams being forced to update RBAC manifests during incidents.
- (decision) AD-3: State ownership — two schema domains. LangGraph owns its langgraph_* tables (checkpoint persistence, black box, no application queries against them). Everything else (incidents, priority queue, case records + vector embeddings, semantic cache, audit log, policy config) is application schema managed by application-owned migrations. Pipeline stages access whatever application tables they need — no per-stage data access restriction. Prevents: coupling application queries to LangGraph internals; LangGraph upgrades breaking application schema.
- (decision) AD-4: Pipeline artifacts = shared types module. All stage-boundary artifacts (Root-Cause Event, Structured Diagnosis Object, Immutable Diagnosis Artifact, Remediation Plan, Case Record) defined in a single shared types/schemas package. All stages import from it. The contract IS the shared types. Because agents produce output via LLMs, structured schema fields coexist with unstructured text fields (e.g. reasoning, prose summaries). Both are first-class parts of the typed artifact. Prevents: incompatible artifact shapes between stages; mapping-layer boilerplate and bugs; schema drift when one stage evolves independently.
- (decision) AD-5: Alert correlation is a deterministic pre-agent triage stage (no LLM). Five-layer correlator: (1) dedup by fingerprint, (2) namespace + temporal proximity, (3) label overlap (node/instance/component) + temporal proximity, (4) static subsystem dependency graph (known OpenShift cascade patterns), (5) Learning Store co-occurrence from past Case Records. Namespace + time or labels + time are each sufficient pairs. Dependency path is sufficient alone. Over-grouping preferred — orchestrator refines during diagnosis. Output: Root-Cause Event artifact containing all grouped alerts + correlation evidence. Prevents: duplicate diagnosis pipelines for symptoms of one failure; conflicting remediations for the same root cause; LLM cost on correlation decisions.
- (decision) AD-6: Severity-based correlation settling windows. Critical=60s, Warning=5m, Info=10m (all Helm-configurable). Group inherits the shortest window of any member alert (severity escalates, never downgrades). Timer resets on each new alert joining. Max group age = 3x settling window as safety cap to prevent indefinite buffering. Prevents: critical alerts waiting in buffer behind slow cascades; low-severity storms sealing too fast and missing related alerts.
- (decision) AD-7: LLM integration = direct per-agent config (no centralized gateway). Each agent role (orchestrator, specialists, skeptics, remediation planner) has its own LLM client configured with endpoint/model/params via Helm values. LangGraph nodes call the LLM directly. Model routing is a wrapper that selects the per-agent config based on task complexity before the call. Semantic cache is a middleware layer intercepting calls before they reach the LLM. Retry/backoff is per-client. Prevents: unnecessary internal service hop in a single-application deployment; over-engineering with a gateway service when LangGraph's native model binding per node handles the per-agent config naturally.
- (decision) AD-8: Backend language = Python. LangGraph primary SDK is Python, richest LLM tooling ecosystem, natural fit for FastAPI REST API, pgvector client libraries, and agentic skills consumption. Frontend is React+TypeScript (settled by UX spine). MCP Server is Go (external binary, not our code). Prevents: fighting the LangGraph/LLM ecosystem with a secondary SDK; splitting the backend across languages.

- (decision) AD-9: Service/pod topology — five deployments. (1) backend: FastAPI REST API + webhook receiver + LangGraph agent pipeline in one Python process. (2) frontend: React standalone web app (static assets, nginx). (3) postgresql: PostgreSQL 18 + pgvector, PVC-backed. (4) mcp-readonly: kubernetes-mcp-server with cluster-reader SA, --read-only flag. (5) mcp-readwrite: kubernetes-mcp-server with cluster-admin SA. API and pipeline collapsed into one deployment for simplicity — checkpoint persistence means in-flight pipelines survive pod restart. MCP instances remain separate deployments because they enforce the RBAC Airlock via distinct ServiceAccounts. Prevents: unnecessary pod count in a single-namespace deployment; split-brain between API state and pipeline state.
- (decision) AD-10: Frontend-backend communication = SSE for real-time pipeline updates + path-versioned REST API (/api/v1/...). FastAPI serves SSE endpoints natively for live pipeline stage transitions and incident state changes. Frontend subscribes to SSE stream on incident detail view, falls back to polling if connection drops. REST API for all CRUD operations (incidents, diagnoses, remediations, approvals, config, stats). URL-path versioning (/api/v1/) for clean, proxy-friendly evolution. Prevents: 5-second polling latency on pipeline transitions that matter to an SRE watching live; header-negotiation complexity for API versioning.
- (decision) AD-11: Observability — in-process /metrics endpoint via prometheus-client Python library. Helm chart includes ServiceMonitor for Prometheus Operator discovery. Structured JSON logging to stdout (standard K8s convention). LangGraph built-in tracing for agent execution traces (stored in PostgreSQL checkpoints, queryable). Prevents: unnecessary sidecar container complexity; non-standard log formats requiring custom parsing.

- (decision) Gap fix (reconciliation): MCP timeout graceful degradation — MCP timeouts produce partial-evidence continuations. The Structured Diagnosis Object carries an evidence_gaps field listing what could not be queried. The Skeptic must challenge any evidence gap. The Policy Gate blocks auto-execution when evidence_gaps is non-empty. Prevents: silently incomplete diagnoses reaching auto-remediation.
- (decision) Gap fix (reconciliation): Stale-remediation re-validation — the execution stage re-validates that the originating alert is still firing and the diagnosis is still relevant before executing. Stale remediations (alert resolved during wait, or cluster state changed by prior remediation) are skipped. This is a backward-looking freshness gate within the pipeline (AD-1). Already specified in FR-15 but now explicit as an architectural invariant.
- (decision) Gap fix (reconciliation): Semantic cache invalidation uses a cluster-context fingerprint at query time (OCP version + topology hash). Cache hits are only valid when the current fingerprint matches the stored one. No background reconciler — staleness is detected at lookup. Prevents: stale cached diagnoses applied to a changed cluster.
- (decision) Gap fix (reconciliation): Resolved-webhook effect on in-flight pipelines — let pipelines complete, skip at execution gate. A resolved webhook during diagnosis does not cancel the pipeline (LangGraph interrupt adds complexity). Instead, the execution stage freshness check (FR-15) catches it: alert no longer firing → skip execution, store diagnosis as informational case record. Prevents: complex cancellation logic; losing diagnostic work that could be valuable for the Learning Store.
- (decision) AD-18: Global remediation lock = PostgreSQL advisory lock. Acquired before execution, released after outcome observation + cooldown. Row-level in a dedicated remediation_locks table (survives pod restart). No other locking mechanism permitted. Cooldown configurable via Helm. Prevents: two epics implementing conflicting lock mechanisms for serialized execution.

- (decision) AD-24 (new): Pipeline→API event delivery via in-process async event bus. Since backend is a single Python process (AD-9), pipeline stages emit typed events to an asyncio queue/bus within the same process. The SSE endpoint in api/ subscribes to this bus. No external message broker, no polling DB for changes. The event envelope (AD-21) is the contract; the bus is the transport. Prevents: two epics inventing incompatible transports (Redis, DB polling, etc.) for pipeline→UI events.
- (decision) AD-19 amended: Incident state-write ownership refined. Three categories: (1) API-permitted writes: incident creation (webhook receiver), approval/rejection (advances awaiting_approval→executing or →failed), resolved-webhook cancellation of queued items (status='queued'→cancelled). (2) Pipeline-only writes: all other state transitions (correlating, diagnosing, diagnosed, executing, observing, resolved, failed). (3) The rule 'only pipeline advances state' now reads 'only pipeline advances state through the diagnosis/execution flow; api/ owns ingress (creation), approval, and cancellation transitions.' Prevents: epics defining incompatible lifecycle states; API team unable to build approval flow.
- (decision) AD-18 amended: Global remediation lock = row-level lock via SELECT FOR UPDATE on a dedicated remediation_locks table. NOT an advisory lock (advisory locks are session-scoped and don't survive pod restart). Single row per namespace, acquired with SELECT FOR UPDATE NOWAIT before execution, held through outcome observation + cooldown, then released. Survives pod restart (lock auto-releases on connection drop; next pod acquires cleanly). Prevents: two epics implementing conflicting lock mechanisms.
- (decision) AD-20 amended: Case Record query interface is dual-mode. (1) Semantic similarity via pgvector (for 'find past diagnoses similar to this alert context'). (2) Relational co-occurrence via standard SQL (for 'which alert fingerprints historically fire together' — AD-5 layer 5). Correlation layer may use BOTH query modes. The constraint remains: schema ownership is Learning Store only; correlation reads via defined query interfaces. Prevents: correlation epic forced into vector-only access when it needs discrete set membership.
- (decision) AD-7 amended: LLM config layering. Helm values provide the initial seed (endpoint, model, params per agent role). Runtime API mutations are persisted to the application DB and take precedence over Helm values. On pod restart, the system loads Helm defaults then overlays any DB-stored runtime overrides. All runtime changes are audit-logged. Prevents: config epic and deployment epic producing conflicting configuration paths with no merge semantics.
- (decision) AD-25 (new): Audit log ownership — cross-cutting middleware. A single audit-log middleware in api/ intercepts all state-changing REST requests and logs them. Pipeline-internal mutations (state transitions, case record writes) are audit-logged by a pipeline audit hook registered once at graph construction. Both write to the same audit_log table in the application schema (AD-3). No per-module ad-hoc audit writes. Prevents: duplicate audit entries or missed mutations from independent implementations.
