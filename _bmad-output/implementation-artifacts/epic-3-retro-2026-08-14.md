## What Didn't Go Well

### 1. Unhappy-Path Scenarios Were Systematically Under-Specified

The dominant review finding pattern across all 5 stories was missing failure-mode handling:
- **3.1:** Plan validation didn't guard against malformed artifact
- **3.2:** Rebuttal failures looked like clean passes (no degraded signal)
- **3.3:** Non-exception MCP error payloads treated as success
- **3.4:** SSE emission failures could crash approval state transitions
- **3.5:** Non-crash-safe execution cycles; recovery lock contention

These weren't edge cases — they were fundamental "what if this external call fails?" scenarios that should have been considered during story specification. The review process caught them, but at the cost of additional rounds.

**Root cause:** Story acceptance criteria focused on the happy path. Neither the story spec process nor the project rules explicitly required failure-mode analysis.

**Fix applied (this session):** Added "Unhappy Path & Failure Mode Discipline" section to `project-context.md` with 5 rules covering:
- Atomic transaction discipline for related writes
- Best-effort SSE emission (never crash the caller)
- Response content validation (not just exception handling)
- Degraded vs. clean outcome distinction
- SSE stage-start/terminal event matching

### 2. Story Files Not Updated After Development

Stories 3.3, 3.4, and 3.5 were all implemented and reviewed but their story files were not updated to `done` status. The `Dev Agent Record` and `Code Review Record` sections in 3.4 and 3.5 were empty until backfilled during this retrospective.

**Root cause:** The dev workflow doesn't enforce a "close out the story file" step after the final review round. Status updates in `sprint-status.yaml` happened, but the story markdown files lagged behind.

### 3. SSE Event Lifecycle Was a Recurring Source of Bugs

SSE event ordering and lifecycle management was flagged in 3 out of 5 stories:
- 3.2: Skeptic `validating` event emitted after work finished; stuck in `validating` on persistence failure
- 3.3: Dry-run `complete` event gated behind policy state transition
- 3.5: Execution completion events coupled to graph node returns

The pattern: emitting start events is easy, guaranteeing terminal events on all code paths (success, failure, exception) is routinely missed.

### 4. Transaction Atomicity Requires Active Vigilance

Audit logging, state transitions, and SSE emission were frequently written outside the primary database transaction. This creates phantom audit trails (claiming validation completed when the data was rolled back) and inconsistent state views.

## Deferred Review Debt Inventory

Both Decision items were resolved during this retrospective session. No deferred debt remains.

### Story 3.1 — Immutable Artifact ID Semantics (RESOLVED)

**Original concern:** `load_immutable_artifact()` overwrites the sealed diagnosis object's `id` with the DB row UUID, technically modifying a read-only artifact that crosses the RBAC Airlock.

**Decision:** Dual-ID approach. Added `diagnosis_object_id` field to `ImmutableDiagnosisArtifact` to preserve the original `DiagnosisObject.id`. The `id` field is set to the DB row PK for FK integrity. Both IDs are persisted in the `immutable_diagnoses` table (migration 014). The artifact carries two identity facets: persistence identity (`id`) and provenance identity (`diagnosis_object_id`).

**Changes:** Model updated, `persist_immutable_diagnosis()` stores both IDs, `load_immutable_artifact()` reads `diagnosis_object_id` from DB column (falling back to JSON-embedded ID for pre-migration rows).

### Story 3.3 — Dry-Run Manifest Payload Gap (RESOLVED — new story needed)

**Original concern:** `apply`/`create` steps carry free-form shell commands but no structured YAML body. Server-side dry-run can't validate the actual resource content.

**Decision:** Add a manifest-generation pipeline stage as a new story. The phase queries current cluster state, generates one or more YAML manifests into a temp folder, and the execution command applies everything in that folder. This separates LLM planning (natural language) from manifest production (structured YAML). `RemediationStep` will need a manifest/artifacts field.

**Changes:** Action item updated in sprint-status.yaml with the design decision. Implementation deferred to a future story.
