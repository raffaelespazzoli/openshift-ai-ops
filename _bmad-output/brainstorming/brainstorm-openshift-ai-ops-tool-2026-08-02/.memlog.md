- (direction) User seeded: operator-deployed, alert-driven, multi-agent diagnosis, adversarial skeptic review, human-or-auto remediation, vector DB learning loop, read-only diagnosis / read-write remediation RBAC split, UI for alerts+diagnosis+remediations, integrates runbooks repo + RHOKP + agentic-skills repos
- (technique) started Ecosystem Thinking — map the tool as an ecosystem: agents, knowledge sources, flows, dependencies
- (idea by coach) Triage Coral: stateless filter between AlertManager and diagnosis agents — deduplicates alert storms, correlates related alerts into single root-cause events, prevents agent drowning during cascades
- (idea by user) Diagnosis Agent Orchestrator: sits after triage, routes to specialized domain agents (compute, storage, network, extensible). Needed because issues often span subsystems.
- (idea by coach) Orchestrator as hypothesis builder: forms initial subsystem hypothesis from alert metadata + runbook context, dispatches primary specialist first, supports lateral escalation (specialist refers to another specialist), stays alive as session coordinator holding evolving diagnosis state to prevent loops
- (idea by user) Specialists contribute partial or full diagnosis if they believe the issue belongs to them; they run specialized read-only commands to extract more info, then return findings to orchestrator. Orchestrator collates partial diagnoses and synthesizes the full root-cause picture.
- (idea by coach) Food web layering: Specialists feed on live cluster state (cluster-reader SA) + domain-specific agentic-skills. Orchestrator feeds on specialist outputs + runbooks + vector DB + RHOKP. Triage feeds on raw alert stream + grouping rules. Each organism stays lean by accessing only its layer's knowledge.
- (question by user) Architecture choice: (1) orchestrator does diagnosis + specialists only extract info, vs (2) specialists attempt domain-specific diagnosis with confidence levels + orchestrator synthesizes. User sees no value in (1) because orchestrator could run commands itself. Core question: do we need a layered system or can a single agent run all diagnosis phases?
- (decision) Keep multilayer architecture: orchestrator + domain specialists. Specialists have access to knowledge sources (runbooks, RHOKP, vector DB) so they can produce their own diagnosis with confidence level, not just extract raw info.
- (idea by coach) Hybrid dispatch: orchestrator handles simple/clear-runbook alerts solo, spawns specialists only when cross-domain or ambiguous — dynamic fan-out, not fixed pipeline
- (idea by coach) Orchestrator's unique role narrows to: (1) dispatch logic — who to ask and in what order, (2) conflict resolution — stitching partial diagnoses into causal chains, (3) completeness check — quality gate that blocks half-baked diagnoses from reaching remediation
- (idea by user) Adversarial skeptic agent challenges the synthesized diagnosis BEFORE it's accepted. If the skeptic raises valid arguments, those arguments are fed back to the specialists to see how they respond — a debate loop that strengthens or rejects the diagnosis.
- (idea by coach) Debate termination options: (1) round limit, (2) confidence delta, (3) evidence demand — skeptic must propose testable counter-hypotheses the system can verify with commands, turning adversarial loop into scientific method
- (idea by user) 1 challenge round per diagnosis. If diagnosis holds after challenge → move to next phase. If specialist completely changes diagnosis due to challenge → original was bad, new diagnosis gets challenged again. Stability = pass.
- (question by user) Need a metric to determine if post-challenge diagnosis is 'same but rephrased' vs 'fundamentally different'. Vectorization distance (embedding similarity) proposed, open to alternatives.
- (decision) Diagnosis comparison metric: structured diagnosis objects with schema (root_cause_component, failure_mode, causal_chain, affected_resources) + root-cause hash from controlled taxonomy. Deterministic field-level diff for same-vs-different. Embedding distance as fallback for novel failures not yet in taxonomy.
- (idea by coach) RBAC boundary as airlock: diagnosis output becomes immutable artifact, remediation agent receives it read-only, cannot re-diagnose. Asks only: what's the fix, blast radius, and rollback steps.
- (decision) Remediation side: single remediation planner agent (not domain-specialized) + one skeptic to challenge the plan. Simpler than diagnosis side because the hard classification work is done — remediation is execution-focused.
- (idea by coach) Structured remediation plan object: steps (ordered actions with command, target, expected effect), blast_radius, rollback_plan, estimated_risk, preconditions. Same one-round skeptic challenge rule applies.
- (idea by coach) Remediation plan as structured object: steps (ordered actions with command, target, expected effect), blast_radius, rollback_plan, estimated_risk, preconditions. Same one-round skeptic challenge rule applies.
- (decision) Auto-remediation gated by user-configurable policy matrix: severity (existing enum) x blast_radius (enum: workload, namespace, node, cluster). User defines which combinations are auto-safe vs require human approval — even in 'automatic' mode.
- (decision) Third dimension added to auto-remediation policy matrix: diagnosis confidence level. Matrix is now: severity x blast_radius x confidence. All three must pass the user-configured threshold for auto-execution.
- (decision) Remediation success criterion: alert resolves. Simple and pragmatic — the alert started the whole flow, so its cessation is the definition of success. No need for complex multi-signal observation.
- (idea by coach) Case record stored in vector DB: alert signature, root-cause code + structured diagnosis, remediation plan that worked, time-to-resolution, cluster context (version, topology, config). Past successes boost future confidence scores for matching patterns — system gets faster and more decisive over time.
- (question by user) Why capture time-to-resolution? Challenge the need for it in the case record.
- (decision) Capture failures in vector DB too — so the system avoids repeating bad fixes. Temporal decay on confidence: older solutions carry less confidence than newer ones.
- (technique) started Disney Method — Dreamer (anything goes), Realist (how to build it), Critic (what breaks)
- (idea by coach) DREAMER: Predictive mode — watch metrics trending toward thresholds, open pre-alert diagnosis and remediate before AlertManager fires. Users see 'Prevented' entries.
- (idea by coach) DREAMER: Cross-cluster federated learning — anonymized case records shared across clusters, collective immune system for OpenShift.
- (idea by user) DREAMER (scoped): Instead of raw metric prediction, the tool identifies post-hoc that a trend caused the issue and PROPOSES a new Prometheus rule + alert to intercept it next time. Proactive alerting as a learning output, not a runtime mode.
- (direction) Cross-cluster federated learning deferred to future development. Requires metrics aggregation layer not in scope.
- (idea by coach) DREAMER: Simulation/dry-run step before execution — oc apply --dry-run=server, admission webhook validation, RBAC checks, quota checks. Mechanical pre-flight that catches 'will this plan even succeed?' before risking anything.
- (decision) Dry-run always executes before human review. Provides additional confidence signal on mechanical feasibility. Shown to human alongside the plan to inform approval decision.
- (decision) REALIST: OLM-managed operator. LLM is external concern — configurable URL + credentials per agent, supports different models and parameters (e.g. thinking mode) per agent role. Vector DB deployed as part of operator, must be k8s-native. Agent framework TBD via research.
- (insight) Vector DB research: Qdrant is the best fit — Rust-native, lightweight, sub-50ms search, k8s operator available, simple ops profile. Milvus is overkill (needs etcd+MinIO+Pulsar). Our case records won't exceed millions of vectors, making Qdrant ideal.
- (insight) Agent framework research: LangGraph is the clear pick — stateful graph, native human-in-the-loop (interrupt/resume), checkpoint persistence (survives pod restarts), full audit trail, deterministic flow control. Matches our needs: HITL approval, complex branching (diagnosis→skeptic→remediation), long-running workflows, observability.
- (decision) ARCHITECTURE PIVOT: Not an operator/CRD-based system. Deployed via Helm. No CRDs — minimize dependencies on the cluster being healed. If the cluster's API machinery is broken, CRD-dependent tooling could fail. Tool has its own data store, history, events, and API layer. Self-contained.
- (decision) UI delivered two ways: (1) OpenShift Console extension plugin, (2) standalone web app. Both talk to the tool's own API layer.
- (decision) Data stores: PostgreSQL for structured data (incidents, history, config, events, audit trail) + Qdrant for vector embeddings (case records, knowledge retrieval). Both deployed via Helm as part of the tool.
- (idea by user) CRITIC response — alert storm handling: (1) same-alert deduplication via status tracking ('already triaging this alert, ignore duplicates'), (2) priority-based queue for different alert types, (3) configurable parallelism cap — only N alerts processed concurrently.
- (decision) CRITIC response — remediation serialization: only one remediation executes at a time (global lock). Configurable cooldown pause between remediations to observe cluster state settling. Prevents conflicting actions and lets the system re-assess after each intervention.
- (decision) CRITIC response — rollback policy: (1) remediation plans include rollback commands when possible (not always feasible), (2) rollback is NEVER automatic — only human-triggered, (3) a triggered rollback is a clear failure signal, (4) failed remediation+rollback stored in vector DB as negative case to avoid repeating.
- (insight) CRITIC insight: 'worse' is hard to measure objectively beyond 'alert resolved or not'. The tool's scope of judgment is limited to the original alert's resolution — broader cluster health assessment is out of scope for automated decision-making.
- (decision) CRITIC response — LLM reliability: (1) retry with configurable backoff, (2) fallback to secondary LLM endpoint (configurable), (3) vector DB fast-path: if past case matches above configurable similarity threshold with success outcome, skip full LLM diagnosis and replay previous remediation directly. Fast-path is default behavior, not an exception.
- (idea by coach) SWARM: Self-selecting specialists — each specialist watches alerts and claims based on label-matching rules (local rule, no central dispatch). Multiple specialists can claim same alert. Orchestrator just collects and synthesizes. New domains are plug-and-play — deploy specialist, it auto-claims matching alerts.
- (question by user) SWARM challenge: what happens when no specialist claims an alert? Uncovered territory.
- (decision) SWARM: Unclaimed alerts handled by option 3 — orchestrator acts as generalist of last resort AND flags the gap in UI as 'no specialist covers this alert type' to signal coverage needs.
- (question by user) Challenge on claim confidence: we already have diagnosis confidence. How would claim confidence (pre-diagnosis, based on label matching) be used differently? Is it redundant?
- (decision) Drop claim confidence — keep binary claim/no-claim via label matching. Diagnosis confidence is sufficient.
- (idea by user) Queue management: alerts received via webhook from AlertManager, prioritized by urgency + recency (most urgent and most recent first). Queue cleanup via alert renewal: AlertManager periodically re-sends firing alerts — if renewal stops arriving, alert has resolved, dequeue it (possibly verify with AlertManager API).
- (insight) AlertManager webhook sends both 'firing' and 'resolved' status. Two cleanup paths: (1) explicit resolved webhook for instant dequeue, (2) TTL-based expiry with API verification as safety net.
- (technique) started Emerging Tech Collision — force-marry the tool with frontier tech to see what new possibilities emerge
- (insight) RESEARCH: Official OpenShift MCP Server exists (github.com/openshift/openshift-mcp-server aka containers/kubernetes-mcp-server). Go-native, no kubectl dependency, direct K8s API interaction. Supports --read-only mode, multi-cluster, RBAC-respecting, bearer token auth. Can be deployed in-cluster via MCP lifecycle operator. Tech preview from Red Hat.
- (decision) All agents interact with OpenShift via the official OpenShift MCP Server. Two instances deployed: (1) read-only bound to cluster-reader SA for diagnosis, (2) read-write bound to cluster-admin SA for remediation execution only. Security boundary enforced at infrastructure level.
- (idea by coach) EMERGING TECH: Knowledge graph built over time — causal map of cluster-specific failure patterns (not generic OpenShift, but 'how THIS cluster breaks'). Relational structure: alert X caused by Y which cascades to Z. Makes triage smarter with cluster-specific historical causality.
- (decision) SIMPLIFICATION: Drop Qdrant — use PostgreSQL with pgvector extension for BOTH structured data AND vector embeddings. One database, one component to manage. pgvector is sufficient for our scale (case records in the thousands-to-millions range).

- (insight) Core identity: 'OpenShift AI Ops for practitioners' — not a theoretical platform, but a hands-on tool for the people actually running clusters day-to-day.
- (insight) Key synthesis: The tool's philosophy is 'learn from doing' — every incident makes it faster, cheaper, and more decisive. It evolves the cluster's alerting (PrometheusRules), builds cluster-specific failure knowledge (pgvector), and reduces LLM dependency over time (fast-path). A practitioner's co-pilot that gets better with use.
